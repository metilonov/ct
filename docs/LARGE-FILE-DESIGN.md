# Одиночный файл больше рабочего пространства

Статус: только проектирование, не реализовано и не протестировано. Текущий движок возвращает `workspace_or_single_file_limit`, не пытаясь записать такой файл целиком. Sparse файл с логическим размером 150ГБ сам по себе не является доказательством ограниченной буферизации.

## Предлагаемый отдельный режим

Нужен native-модуль libtorrent 2.x с собственным disk_interface (C++), а не вызов обычного file upload для незавершённого файла. Python bindings текущего проекта не предоставляют готовое безопасное bounded-storage решение.

1. Разбить диапазон выбранного файла на окна из целых BitTorrent pieces. Рабочий буфер, например 256–512 МиБ, плюс отдельный резерв для двух граничных pieces и Drive chunk 8 МиБ. Фактический размер снова ограничивается statvfs и общей reservation ledger; параллельные окна учитываются вместе с обычными пакетами.
2. Скачивать окно с приоритетом нужных pieces. Хранить целый piece, включая байты соседних файлов, до проверки BitTorrent-хеша. В Drive передавать только байты выбранного файла, в исходном порядке. Не отправлять непроверенные байты из receive buffer.
3. Google resumable upload принимает блоки, кратные 256 КиБ (кроме последнего). Неполный Drive chunk на границе окна удерживается до следующего окна, а не дополняется вымышленными байтами.
4. После подтверждения Google offset фиксировать транзакционно: torrent/infohash, file index/size, piece window, session URL (зашифрован), acknowledged offset, содержимое оставшегося хвоста, версия storage manifest и состояние проверки целостности. Повторный запуск сначала запрашивает подтверждённый offset у Google.
5. Освобождать piece только после подтверждения всех его потребителей. Нельзя просто удалить bytes, продолжая сообщать libtorrent/пирам, что piece имеется. Native-модуль должен согласовать possession/read callbacks и рекламу pieces. Без доказанной поддержки такого согласования безопаснее закрывать handle после окна и создавать новый с чистой картой доступности для следующего; это дороже и требует отдельного испытания протокола.
6. Подтвердить весь файл по размеру и контрольной сумме. Для восстановления checksum после сбоя нужен проверяемый versioned checkpoint hashing state либо повторное чтение подтверждённого префикса из Drive. Простое сохранение финального MD5-дайджеста префикса не позволяет продолжить MD5. До успешной проверки последнего ответа задача не получает `ready`.

## Обязательные испытания до объявления поддержки

- Реальный легальный файл >10ГиБ при жёсткой filesystem quota меньше размера файла; наблюдать peak disk allocation и RAM.
- Граница piece одновременно принадлежит нескольким выбранным и невыбранным файлам.
- Падение процесса до/после Google ACK и до/после SQLite commit, истечение OAuth и resumable session.
- Повторная выдача pieces пирам после eviction, recheck, повторный запрос окна и отсутствие неверной рекламы имеющихся данных.
- Сетевой разрыв, пропуск/повтор chunk, неверный hash, исчерпание диска другим процессом, cancellation.
- Ни одно состояние после рестарта не удаляет единственную неподтверждённую копию. Тесты должны подтверждать итоговую checksum файла в Drive и максимальный расход, а не только успешный HTTP-ответ.

До реализации этого модуля и испытаний приложение не показывает поддержку streaming для большого одиночного файла. `/server/status` публикует `large_single_file_streaming=false`.
