# Google Drive

Это место назначения файлов; вычисления выполняются BotHost. Используется официальный Drive v3 API, OAuth 2.0. Секреты отсутствуют в APK.

1. В собственном Google Cloud проекте включить Drive API, настроить consent screen и web OAuth client. В режиме Testing добавить тестового пользователя. Это настройка OAuth, не создание Compute Engine.
2. Задать GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, GOOGLE_REDIRECT_URI=https://домен/drive/callback на сервере. Redirect URI должен совпадать с зарегистрированным.
3. Сгенерировать TOKEN_ENCRYPTION_KEY через cryptography.fernet.Fernet.generate_key(); хранить как секрет панели отдельно от /app/data. Не публиковать в Git.
4. Авторизованный POST /drive/authorize возвращает URL. Открыть в браузере и войти в Google самостоятельно. State одноразовый, живёт 10 минут. Секретный refresh token сохраняется AES/Fernet в /app/data/drive.enc с правами 0600.
5. Scope drive.file ограничивает видимость файлами/папками, созданными или явно предоставленными приложению. GET /drive/folders перечисляет доступные папки (первая страница 100); PUT /drive/folder {"id":"..."} задаёт существующую доступную папку. POST /drive/folders создаёт доступную приложению папку Cloud Torrent Client и выбирает её. Это рабочий путь для первого подключения без Google Picker. Можно заранее указать GOOGLE_DRIVE_FOLDER_ID. Полноценный Google Picker UI ещё не реализован. Нельзя считать произвольную папку доступной только по её id.
6. /server/status проверяет OAuth запросом к реальной папке; наличие переменных само по себе не означает подключение.
7. DELETE /drive отзывает credential и удаляет локальный encrypted token.

Загрузка: resumable session, блоки 8 МиБ, проверка offset запросом после сетевой ошибки, до 5 попыток, создание вложенных папок, GET size+md5Checksum после завершения. Только затем в SQLite записывается drive_id; удаление пакета после подтверждения всех файлов.

Восстановление: URL resumable session сохраняется в зашифрованном upload-*.enc, после перезапуска offset запрашивается у Google. Подтверждённые файлы ищутся по appProperties и MD5 перед повторной передачей. Это требует реальных внешних испытаний, включая нулевые файлы, истечение сессий и согласование после сбоя. Передача в реальный аккаунт в этой сессии не проверена. Не включать обслуживание публичных пользователей до завершения этих испытаний и изоляции пользователей.
